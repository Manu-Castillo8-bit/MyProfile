Meta de la fase

Descubrir qué debe hacer el sistema

Esta es la fase más crítica de todo el proyecto: un error aquí se arrastra hasta el final. Vas a recopilar, de forma ordenada, todo lo que el sistema debe hacer y dejarlo escrito en un documento formal: la Especificación de Requerimientos de Software (ERS/SRS).

Lo que entregas

Entregables de la FASE 01

📑
Documento ERS / SRS
El documento central de esta fase, ordenado y con portada.
📝
Ficha del proyecto
Nombre del sistema, problema que resuelve, cliente/institución, tipo (web/escritorio/móvil).
👤
Stakeholders y usuarios
Quién usa o necesita el sistema y qué espera de él.
🔷
Requerimientos funcionales
Lo que el sistema hace, con identificador: RF-01, RF-02...
🔶
Requerimientos no funcionales
Rendimiento, seguridad, usabilidad: RNF-01, RNF-02...
📋
Instrumento de recolección
Entrevista o encuesta aplicada, con evidencia (Google Forms / fotos).
Paso a paso

Cómo levantar los requerimientos

Definan el sistema y el problema
En 3 líneas: ¿qué problema resuelve y para quién? Pónganle nombre.
Identifiquen a los stakeholders
Listen a todas las personas que usarán o influyen en el sistema (dueño, empleados, clientes).
Apliquen una técnica de recolección
Entrevista al "cliente", encuesta a usuarios u observación del proceso actual. Guarden la evidencia.
Redacten requerimientos funcionales
Frases claras y verificables. Ej.: RF-03: El sistema permite registrar una venta.
Redacten requerimientos no funcionales
Ej.: RNF-01: El sistema responde en menos de 3 segundos.
Prioricen con MoSCoW
Marquen cada requerimiento como Must, Should, Could o Won't para esta versión.
Consoliden el ERS
Integren todo en un solo documento ordenado y súbanlo a docs/.
Plantilla

Estructura del documento ERS

No improvises el orden. Usa esta estructura como esqueleto del documento.

ERS.docx — índice
# Estructura mínima del documento ERS / SRS
1. Introducción          # propósito, alcance, definiciones
2. Descripción general    # problema actual, usuarios, supuestos
3. Requerimientos funcionales     # RF-01, RF-02, RF-03 ...
4. Requerimientos no funcionales  # RNF-01: rendimiento, seguridad...
5. Casos de uso (texto)   # actor, precondición, flujo, postcondición
6. Priorización (MoSCoW)  # Must / Should / Could / Won't
Ejemplo guía

Caso: «Tiendita La Bendición»

Sistema de control de inventario y ventas para una tienda de barrio salvadoreña. Este ejemplo nos acompañará en todas las fases.

TipoIDRequerimiento
FuncionalRF-01El sistema permite registrar productos con nombre, precio y stock.
FuncionalRF-02El sistema permite registrar una venta y descontar el stock.
FuncionalRF-03El sistema muestra el stock disponible de cada producto.
FuncionalRF-04El sistema genera un reporte de ventas por día.
No funcionalRNF-01El sistema funciona en una laptop con 4 GB de RAM.
No funcionalRNF-02Solo el administrador puede eliminar productos (acceso por rol).
💡 Elijan algo cercano
Una pupusería, la biblioteca del instituto, una clínica comunal, un taller mecánico, una agrotienda. Mientras más conozcan el proceso real, mejores requerimientos van a escribir.

Entrega

Cómo y dónde entregar

Suban el documento a la carpeta docs/ del repositorio y registren el avance con un commit.

terminal
git add docs/ERS.pdf
git commit -m "docs: ERS con requerimientos funcionales y no funcionales (FASE 01)"
git push
⚠️ Errores comunes
Requerimientos vagos ("que sea bonito"), confundir lo que el sistema hace con cómo se ve, y olvidar los no funcionales. Un buen requerimiento se puede probar: si no se puede verificar, está mal redactado.
